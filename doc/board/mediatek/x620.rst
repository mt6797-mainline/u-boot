LeEco X620: stock-LK U-Boot relay
================================

This experimental MT6797 port runs U-Boot proper as the kernel payload of
an Android v0 boot image. Stock preloader, ATF and LK remain responsible for
DRAM, PMIC, PLL and panel initialization. No SPL or replacement LK is built.

The LK-facing payload is a gzip stream followed by the original hardware
DTB. The decompressed U-Boot has an ARM64 Linux Image header with text_offset
0x80000 and entry 0x40080000. The gzip stream contains the entire U-Boot
binary including its own separate control DTB; the original hardware DTB
is appended outside that stream. The workspace packager retains the
original ramdisk blob to reproduce the usual LK loading path. It is not
executed by U-Boot.

Memory and handoff
------------------

The entry hook saves x0-x3, CurrentEL and SCTLR into initialized data. With
the MMU disabled it writes a persistent entry marker and disables the AP
RGU watchdog before setting up the C runtime. PMIC/SPM watchdogs are not
controlled by this first implementation. A previous 24-second restart has
not been proven to originate in AP RGU.

Only 0x48000000..0x50000000 is offered to the U-Boot allocator. This keeps
relocation, stack and malloc away from stock ATF, LK, DTB, ramdisk and RAM
console. The fastboot download area is 0x48000000..0x4c000000, below the
observed relocation/malloc region. The first 512 MiB of DDR has a normal
memory mapping. The measured framebuffer range at 0xbd000000..0xbf000000
has a separate noncacheable mapping and is not allocator RAM.

After relocation, LMB also admits low DDR at 0x40000000..0x48000000 for
Linux Image placement. Explicit no-overwrite reservations protect LK, ATF,
preloader data, RAM console and the LK DT workspace; the download buffer is
also reserved. This does not widen the C heap or relocation window. FDT
memory fixup from the restricted U-Boot DRAM bank is disabled so Linux
keeps the memory description from its own DT.

Persistent markers occupy the first page of the vendor console zone at
0x444bf000. They use its signature/start/size header layout. Recovery can
still clear these bytes; absence of a marker does not prove no entry.

Display and USB
---------------

The retained display driver accepts only the live packed videolfb tag for
panel 378C81, bounded to the mapped framebuffer range. It checks OVL0,
layer-0 address and pitch, and DSI0 command mode before removing the logo
overlay and disabling layer-0 alpha blending for U-Boot's XRGB8888 pixels.
DSI BUSY makes the refresh callback return immediately and retry
at a later sync; it never polls through udelay(), which would schedule a
second video refresh from inside the first. It does not implement full
panel, DDP or power-domain bring-up.
The owner confirmed screen text and USB operation after flashing the image
with this takeover fix; no manual register changes were needed after boot.

USB uses the upstream MTU3 gadget driver with MT6797 MAC/IPPC addresses
and a board-specific USB2 PHY recovery sequence derived from the reference
kernel. A board clock provider exposes the three required bus/sys/ref clocks
and ungates their INFRA2 bits while retaining LK's PLL/mux selections.
Supply and PLL calibration are inherited from LK; Type-C policy
and PMIC initialization are not implemented. USB3 operation is disabled.
Fastboot flashing is disabled. Download, FIT/Android boot support and
``fastboot oem console`` are compiled in, with a diagnostic polling loop.
Fastboot enumeration, console reads and OEM shell commands have been
validated on hardware. The owner subsequently confirmed visible Linux
startup after the download-boot test with the deferred handoff below.

The default boot command prints handoff diagnostics, attempts USB fastboot,
and remains in U-Boot with a five-second heartbeat. It does not automatically
boot Linux. A UART Ctrl-C returns to the U-Boot shell; USB fastboot
``continue`` exits the USB loop into the heartbeat command.

Downloaded Linux and stock LK relocking
--------------------------------------

Static analysis of the owner's LK backup found that its fastboot ``reboot``
and ``reboot-bootloader`` handlers call a shared lock flow at 0x4602b8bc.
Its ``boot`` handler calls that flow before jumping and on a failure path.
The flow reaches the same lock helper as ``oem lock`` and invokes the lock
state updater with argument 1. Avoid those stock LK commands for bring-up.

X620 overrides U-Boot's default fastboot boot callback to queue the request.
The USB loop unregisters the gadget and releases the UDC before executing
``bootm 0x48000000`` (or an explicit ``fastboot_bootcmd`` override). If the
loader returns, the loop reopens fastboot instead of resetting the phone.
This prevents a malformed download from discarding its error report and
keeps kernel handoff outside the gadget completion callback. It does not
modify LK or the device's stored unlock state. An explicit U-Boot reboot
still restarts through stock firmware; boot firmware effects are untested.

The companion workspace builds ``dist/linux-boot.img`` as an Android v2 RAM
download payload, containing a gzip Linux 6.12 Image, diagnostic initrd and
a distinct mainline board DT. ``dist/boot.img`` remains the stock LK-facing
U-Boot relay image. Download Linux with ``fastboot boot linux-boot.img`` only
after confirming serial ``X620-UBOOT-RELAY`` and the U-Boot version response.
Do not flash the Linux RAM payload over the relay's boot partition.

The first Linux profile uses one CPU and 512 MiB of RAM, preserves firmware
clocks and power domains, and uses simplefb plus a guarded command-mode
refresh worker. A temporary early console writes the vendor-compatible
persistent log at 0x444bf000, expanding from one page to 64 KiB once ioremap
is available. Linux USB gadget support on this board is not wired up yet;
loss of the U-Boot USB function after kernel entry is expected. The new
Android bootm path, diagnostic PID 1 and retained-display refresh worker
passed QEMU tests with virtual UART and RAM register fixtures. Actual
The owner confirmed seeing the requested Linux startup output on X620 on
2026-10-13. This is an owner-reported boot milestone, without captured device
logs or shell access; USB gadget and storage support remain unvalidated.

Autoboot uses a delay of -2 to bypass UART-key abort checks. Text now goes to
both serial and vidconsole after correcting layer blending. Output is also
recorded for ``fastboot oem console``. Serial-only output was used to isolate
the display failure while bringing up USB.
``fastboot oem run:'x620diag'`` can run diagnostics once USB is available.
Persistent main-loop and diagnostic-command markers bracket console output;
the main-loop marker captures counter frequency, UART LSR and display state.

ARM64 fatal exception handlers record the first ESR, FAR, ELR, link-time PC
and x0-x3 before attempting console output. PANIC_HANG keeps fatal reports
in RAM until manual reset. A power-off can still discard those records.

Build and validation
--------------------

Hardware validation on 2026-10-13 used the 3,051,520-byte boot image with
SHA256
``2cbb31c29f482b6935279a2d624e7d058be2fcfbf838d9de50f6d8afd8ac5240``.
After flashing, the owner confirmed both display and USB working at startup.
This image is preserved as the tested binary; committing its sources does
not rebuild or replace it merely to update the version banner.

Earlier live tests confirmed EL2 entry, CNTFRQ 13 MHz, a valid LK DTB at
0x44000000, relocation at 0x4ff9e000, and at least 130 seconds of diagnostic
heartbeats. Windows fastboot identified ``X620-UBOOT-RELAY`` and returned the
console log and OEM register reads.

The display diagnosis was verified independently of the text renderer:
opaque white written to 0xbd0c0000..0xbd8b8000 appeared after selecting layer
0 and pulsing mutex 0 and DSI_START. Reading back a rendered X found the
expected bitmap with foreground 0x00c0c0c0, while L0_CON was 0x21ff. Clearing
only AEN (L0_CON=0x20ff) made the glyph visible. Diagnostic text and five-second
USB heartbeats then appeared with serial and vidconsole output enabled.

The first USB DT lacked mandatory clocks, so clk_get_bulk() returned before
PHY setup. The three clock specifiers and INFRA2 gate provider now allow
probe to reach the controller. The diagnostic command retains the underlying
probe errno instead of the generic UDC helper's masked -ENODEV.

Software validation includes an ARM64 cross-build, boot container and
measured partition-size checks, QEMU entry/relocation/60-second heartbeat and
Linux rescue /init handoff, a 10,000-call BUSY callback test, alpha-bit
preservation checks and injected translation-fault recording. QEMU does not
emulate the MT6797 display or USB hardware. The subsequent Linux download
test received the owner's confirmation of visible startup. eMMC loading,
Linux USB gadget support and USB3 remain outside the validated capabilities.

The source checkout includes ``board/mediatek/x620/mt6797_x620.config`` as the
initial production build configuration. To build the U-Boot binary alone::

    mkdir -p /tmp/x620-uboot-build
    cp board/mediatek/x620/mt6797_x620.config /tmp/x620-uboot-build/.config
    make O=/tmp/x620-uboot-build CROSS_COMPILE=aarch64-linux-gnu- olddefconfig
    make O=/tmp/x620-uboot-build CROSS_COMPILE=aarch64-linux-gnu- -j10 u-boot.bin

Reuse that output directory for later builds. This builds the relay binary;
Android boot-image packaging also needs the stock device DTB and ramdisk.

The workspace uses an external ``cfg/x620-uboot.config`` rather than modifying
an existing source defconfig. ``scripts/build-uboot.sh`` reuses ``out/u-boot``
and produces fixed ``dist/boot.img`` and ``dist/u-boot.bin`` names. The package
is checked against the device's measured 16 MiB boot partition.

``scripts/build-uboot-qemu.sh`` builds the same X620 board code with a test-only
PL011 control DT. ``scripts/test-uboot-qemu.py`` supplies the real captured LK
DT at 0x44000000 through a register-setting shim, checks entry and relocation
markers and a 60-second heartbeat, then exercises ``booti`` with the archived
Linux rescue payload. It does not emulate MT6797 display, USB or watchdog IO.
The USB fixture supplies the production resource bindings with a RAM-backed
zero IPPC status region. It verifies all three clock requests, PHY setup and
an expected hardware-clock timeout without claiming USB enumeration support.
``scripts/test-uboot-qemu.py --fault-only`` injects a translation fault and
checks the persistent exception report before console output.
